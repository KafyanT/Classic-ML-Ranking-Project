# Ранжирование объявлений в поиске: отчёт об экспериментах

Код: [`Ad_Ranking_Colab.ipynb`](Ad_Ranking_Colab.ipynb). Номера разделов ниже совпадают с разделами ноутбука.

## Задача

Для каждого запроса (`query_id`) отсортировать объявления по убыванию релевантности. Релевантность — `item_contact` (был ли контакт с продавцом), метрика — NDCG@10. Сабмит — `solution.csv` с колонками `query_id`, `item_id`.

## Итог

| | NDCG@10 |
|---|---|
| baseline: сортировка по `click_conv` (фолд 0) | 0.4392 |
| **итоговая модель, валидация на 5 фолдах (раздел 6)** | **0.5137 ± 0.0013** |
| лучший вариант на псевдо-выдачах, похожих на test (раздел 7) | 0.4843 |

Правильных ответов для test нет, поэтому качество оценивается только на валидации.

## 1–2. Данные и EDA

- train: 7.78M строк, 678k запросов; test: 335k строк, 12.5k запросов.
- Текст описаний занимает ~6.4 из 7.5 ГБ train и не помещается в память Colab — загружается только его длина.

| Наблюдение | Решение |
|---|---|
| ~4.4% позитивов; у ~64% запросов нет контактов | выдачи без контраста (все 0 или все 1) не дают градиента lambdarank и не входят в NDCG — убраны из обучения |
| **train собран окнами**: в выдачах из 11 строк контакт в ~97% случаев ровно в середине (5 соседей сверху + контакт + 5 снизу) | позиция строки — утечка (с ней NDCG на валидации ≈ 0.79, на test не работает); не используется, строки внутри запроса перемешаны |
| медиана выдачи: train 11, test 34; в train нет нерелевантного «хвоста» выдачи | только относительные признаки (ранги/доли внутри выдачи); обучение на длинных псевдо-выдачах (раздел 7) |
| `click_conv = -1` у ~85% строк — «нет статистики» | NaN + флаг `conv_missing` |
| `query_cat = 0` (~22%), `query_loc = 0` (~16%) — «не определено» | null; признаки совпадения для них null |
| цена 0 у ~8% строк, contact rate у них ~7.9% (вакансии, услуги); выбросы до 1e12 | флаг `price_missing`, `log1p`, цена относительно выдачи |
| пересечение слов запроса и заголовка монотонно связано с контактом; много артикулов и латиницы | TF-IDF по словам и символьным n-граммам, BM25, эмбеддинги |
| ~14% строк — копии заголовков внутри выдачи, ~13% повторяющихся пар (запрос, объявление) с разным таргетом | шум ограничивает потолок NDCG; `title_dups`, история по заголовку |
| запросы test не встречаются в train, но ~66% их текстов и ~35% объявлений есть в train | фолды по `query_id`; история по тексту запроса и объявлению — out-of-fold |

## 3. Валидация

- 5 фолдов, разбиение по `query_id`: все строки запроса в одном фолде.
- NDCG@10 — одна функция для всех моделей: среднее по запросам с хотя бы одним контактом, ничьи разбиваются случайно.
- Фолд 0 — для сравнения шагов, 5 фолдов — для итоговой оценки.
- Target encoding и оценки cross-encoder для train считаются только по данным, которые строка «не видела» (out-of-fold).
- Абсолютный NDCG на окнах train не равен скору на test (выдачи test втрое длиннее), поэтому сравниваются модели между собой; дополнительно — валидация на псевдо-выдачах, похожих на test.

## 4–6. Эксперименты

NDCG@10 на фолде 0 (таблица `validation` в разделе 8 ноутбука):

| Шаг | Что добавлено | NDCG@10 |
|---|---|---|
| random | — | 0.4293 |
| сортировка по `click_conv` | baseline без обучения | 0.4392 |
| LightGBM: tabular | `lambdarank`; конверсия, цена (абсолютная и относительно выдачи), совпадение категории / региона, длины текстов | 0.4771 |
| + text + target encoding | TF-IDF (слова, символьные 3–5-граммы), BM25, доля слов запроса в заголовке, эмбеддинги `rubert-tiny2`, их ранги и отставания внутри выдачи; out-of-fold target encoding объявления, пары (запрос, объявление), категорий, регионов | 0.5093 |
| + extra TE + point features | история по заголовку и по (запрос, категория / регион); совпадение чисел и артикулов, длина и частота запроса, разнообразие выдачи, копии заголовков | 0.5145 |
| cross-encoder alone | `rubert-tiny2`, дообученный на парах запрос–заголовок (BCE), без LightGBM | 0.4614 |
| + cross-encoder | `ce_score` и его ранг / отставание внутри выдачи | 0.5138 |
| **итоговая модель, 5 фолдов** | ансамбль 5 моделей | **0.5137 ± 0.0013** |

Важность признаков итоговой модели — график в разделе 6 ноутбука.

Cross-encoder сам по себе лучше baseline (0.461 против 0.439), но в LightGBM прироста не дал (0.5145 → 0.5138, в пределах разброса между фолдами ± 0.0013): его сигнал уже покрыт TF-IDF, BM25 и target encoding.

**Почему прирост над baseline выглядит небольшим.** Негативы в окнах — соседи объявления с контактом в исходной выдаче, то есть объявления, которые поисковик уже счёл почти такими же релевантными. Вместе с шумом разметки это ограничивает достижимый NDCG на такой валидации.

### Обоснование методов

- **LightGBM `lambdarank`** напрямую оптимизирует NDCG через попарные сравнения внутри выдачи; градиентный бустинг хорошо работает с разнородными табличными признаками, пропусками и категориями.
- **Относительные признаки** (`*_rank`, `*_gap`): абсолютное сходство несравнимо между запросами, а для сортировки важно, лучше ли объявление соседей по выдаче.
- **TF-IDF + BM25 + эмбеддинги** дополняют друг друга: точные совпадения слов, словоформы и артикулы, смысловая близость без общих слов.
- **Target encoding со сглаживанием** превращает id с сотнями тысяч значений в понятный модели признак «как часто здесь был контакт»; out-of-fold — чтобы признак не содержал собственный таргет.
- **Cross-encoder** читает пару запрос–заголовок целиком и учится на контактах, а не на «похожести текстов». Оценки для train получены моделью, не видевшей эти строки (две половины фолдов).
- **5-фолдовый ансамбль**: оценка на одном фолде шумит на ±0.003; среднее 5 моделей стабильнее одной.

## 7. Длинные выдачи

Окна с одинаковым текстом запроса внутри одного фолда склеены в псевдо-выдачи до 50 объявлений, относительные признаки пересчитаны по ним. NDCG@10 на псевдо-выдачах валидационных фолдов:

| Вариант | все псевдо-выдачи | только 25+ объявлений |
|---|---|---|
| random | 0.3937 | 0.1810 |
| сортировка по `click_conv` | 0.4027 | 0.1968 |
| модель, обученная на окнах (раздел 6) | 0.4783 | 0.2662 |
| модель, обученная на псевдо-выдачах | 0.4834 | **0.2844** |
| среднее двух моделей | **0.4843** | 0.2834 |

Вывод: обучение на псевдо-выдачах лучше обучения на окнах, и разница растёт с длиной выдачи: +0.005 на всех псевдо-выдачах и +0.018 (+7%) на выдачах из 25+ объявлений. Модель, обученная только на окнах, хуже отсекает дальний хвост выдачи, которого в окнах train нет. На всех псевдо-выдачах лучшее — среднее двух моделей, оно записано в основной `solution.csv`; на самых длинных выдачах лучшая — модель на псевдо-выдачах (`solution_alt1.csv`).

## Что не сработало

- **Позиция строки в выдаче** — утечка из-за устройства train (окна вокруг контакта): NDCG ≈ 0.79 на валидации, бесполезна на test. Удалена.
- **Сырые id подкатегорий, регионов и объявлений как признаки** — миллионы значений, модель переобучается; заменены target encoding и признаками совпадения.
- **Полный текст описаний** — не помещается в память Colab; используется только длина.

## Воспроизведение

1. Положить `train-dset.parquet` и `test-dset-small.parquet` в корень Google Drive.
2. Открыть `Ad_Ranking_Colab.ipynb` в Colab, Runtime → Change runtime type → T4 GPU.
3. Runtime → Run all. Все случайности фиксированы `SEED = 42`. Эмбеддинги и оценки cross-encoder кешируются на Drive.
4. Результат — `solution.csv` (и `solution_alt*.csv`) в корне Drive.
