# Ранжирование объявлений в поиске: отчёт об экспериментах

Код: [`Ad_Ranking_Colab.ipynb`](Ad_Ranking_Colab.ipynb) (для ревью — та же версия в [`ad_ranking_colab.py`](ad_ranking_colab.py)). Номера разделов ниже совпадают с разделами ноутбука.

## Задача

Для каждого запроса (`query_id`) отсортировать объявления по убыванию релевантности. Релевантность — `item_contact` (был ли контакт с продавцом), метрика — NDCG@10. Сабмит — `solution.csv` с колонками `query_id`, `item_id`.

## Итог

| | NDCG@10 |
|---|---|
| baseline: сортировка по `click_conv` (фолд 0) | 0.4535 |
| **итоговая модель, валидация на 5 фолдах (раздел 6)** | **0.5244 ± 0.0007** |
| лучший вариант на псевдо-выдачах, похожих на test (раздел 7) | 0.4978 |

Правильных ответов для test нет, поэтому качество оценивается только на валидации.

### Исправления после ревью

1. **Утечка через признаки из таргета.** Target encoding и оценки cross-encoder считались один раз для всех разбиений, поэтому обучающие строки получали статистику, посчитанную в том числе по таргетам валидационного фолда. Теперь они пересчитываются для каждого разбиения только по его обучающей части (раздел 3).
2. **Метрика.** Запросы, где контакт у всех, раньше удалялись до валидации. Теперь они не участвуют только в обучении, а в NDCG@10 остаются (у них NDCG = 1).
3. **Воспроизводимость.** Зафиксированы seed PyTorch и версии библиотек.
4. **Cross-encoder** после исправления утечки ухудшает итоговую модель и оставлен как эксперимент (раздел 5.4 ноутбука).

**Почему цифры выросли, хотя утечку убрали.** Запросы «контакт у всех» — 2.6% запросов валидации, и каждый добавляет в среднее NDCG = 1. Поэтому выросли все строки таблиц, включая baseline без обучения (`click_conv`: 0.4392 → 0.4535). Если пересчитать новые цифры к старому определению метрики (без этих запросов):

| Шаг | до исправлений | после, в старой шкале |
|---|---|---|
| сортировка по `click_conv` (фолд 0) | 0.4392 | 0.4395 |
| LightGBM: tabular (фолд 0) — признаков из таргета нет | 0.4771 | 0.4780 |
| + extra TE + point features (фолд 0) | 0.5145 | 0.5129 |
| **итоговая модель, 5 фолдов** | **0.5137** | **0.5117** |

Модели без признаков из таргета совпадают, а итоговая после исправления утечки на ~0.002 ниже: на столько была завышена прежняя оценка.

## 1–2. Данные и EDA

- train: 7.78M строк, 678k запросов; test: 335k строк, 12.5k запросов.
- Текст описаний занимает ~6.4 из 7.5 ГБ train и не помещается в память Colab — загружается только его длина.

| Наблюдение | Решение |
|---|---|
| ~4.4% позитивов; у ~64% запросов нет контактов | выдачи без контраста (все 0 или все 1) не дают градиента lambdarank — убраны из обучения; выдачи без контактов не входят и в NDCG, а выдачи «контакт у всех» в метрике остаются (NDCG = 1) |
| **train собран окнами**: в выдачах из 11 строк контакт в ~97% случаев ровно в середине (5 соседей сверху + контакт + 5 снизу) | позиция строки — утечка (с ней NDCG на валидации ≈ 0.79, на test не работает); не используется, строки внутри запроса перемешаны |
| медиана выдачи: train 11, test 34; в train нет нерелевантного «хвоста» выдачи | только относительные признаки (ранги/доли внутри выдачи); обучение на длинных псевдо-выдачах (раздел 7) |
| `click_conv = -1` у ~85% строк — «нет статистики» | NaN + флаг `conv_missing` |
| `query_cat = 0` (~22%), `query_loc = 0` (~16%) — «не определено» | null; признаки совпадения для них null |
| цена 0 у ~8% строк, contact rate у них ~7.9% (вакансии, услуги); выбросы до 1e12 | флаг `price_missing`, `log1p`, цена относительно выдачи |
| пересечение слов запроса и заголовка монотонно связано с контактом; много артикулов и латиницы | TF-IDF по словам и символьным n-граммам, BM25, эмбеддинги |
| ~14% строк — копии заголовков внутри выдачи, ~13% повторяющихся пар (запрос, объявление) с разным таргетом | шум ограничивает потолок NDCG; `title_dups`, история по заголовку |
| запросы test не встречаются в train, но ~66% их текстов и ~35% объявлений есть в train | фолды по `query_id`; история по тексту запроса и объявлению — только по обучающей части каждого разбиения |

## 3. Валидация

- 5 фолдов, разбиение по `query_id`: все строки запроса в одном фолде.
- NDCG@10 — одна функция для всех моделей: среднее по запросам с хотя бы одним контактом (включая выдачи, где контакт у всех), ничьи разбиваются случайно.
- Фолд 0 — для сравнения шагов, 5 фолдов — для итоговой оценки.
- Target encoding и оценки cross-encoder пересчитываются для каждого разбиения только по его обучающей части: обучающая строка фолда `f` в разбиении `k` получает признаки без таргетов фолдов `f` и `k`, строки валидационного фолда `k` и test — без таргетов фолда `k`.
- Выдачи, где контакт у всех (~2.6% запросов), не дают пар для lambdarank и в обучение не идут, но остаются в валидации.
- Абсолютный NDCG на окнах train не равен скору на test (выдачи test втрое длиннее), поэтому сравниваются модели между собой; дополнительно — валидация на псевдо-выдачах, похожих на test.

## 4–6. Эксперименты

NDCG@10 на фолде 0 (таблица `validation` в разделе 8 ноутбука):

| Шаг | Что добавлено | NDCG@10 |
|---|---|---|
| random | — | 0.4424 |
| сортировка по `click_conv` | baseline без обучения | 0.4535 |
| LightGBM: tabular | `lambdarank`; конверсия, цена (абсолютная и относительно выдачи), совпадение категории / региона, длины текстов | 0.4911 |
| + text + target encoding | TF-IDF (слова, символьные 3–5-граммы), BM25, доля слов запроса в заголовке, эмбеддинги `rubert-tiny2`, их ранги и отставания внутри выдачи; target encoding (по разбиениям) объявления, пары (запрос, объявление), категорий, регионов | 0.5220 |
| + extra TE + point features | история по заголовку и по (запрос, категория / регион); совпадение чисел и артикулов, длина и частота запроса, разнообразие выдачи, копии заголовков | **0.5251** |
| **итоговая модель, 5 фолдов** | признаки предыдущего шага, ансамбль 5 моделей | **0.5244 ± 0.0007** |
| *эксперимент:* cross-encoder alone | `rubert-tiny2`, дообученный на парах запрос–заголовок (BCE), без LightGBM | 0.4688 |
| *эксперимент:* + cross-encoder | `ce_score` и его ранг / отставание внутри выдачи | 0.5231 |

Важность признаков итоговой модели — график в разделе 6 ноутбука.

Cross-encoder сам по себе лучше baseline (0.469 против 0.454), но в LightGBM ухудшает результат (0.5251 → 0.5231, втрое больше разброса между фолдами ± 0.0007): его сигнал уже покрыт TF-IDF, BM25 и target encoding. Поэтому в итоговую модель он не входит и оставлен как эксперимент.

**Почему прирост над baseline выглядит небольшим.** Негативы в окнах — соседи объявления с контактом в исходной выдаче, то есть объявления, которые поисковик уже счёл почти такими же релевантными. Вместе с шумом разметки это ограничивает достижимый NDCG на такой валидации.

### Обоснование методов

- **LightGBM `lambdarank`** напрямую оптимизирует NDCG через попарные сравнения внутри выдачи; градиентный бустинг хорошо работает с разнородными табличными признаками, пропусками и категориями.
- **Относительные признаки** (`*_rank`, `*_gap`): абсолютное сходство несравнимо между запросами, а для сортировки важно, лучше ли объявление соседей по выдаче.
- **TF-IDF + BM25 + эмбеддинги** дополняют друг друга: точные совпадения слов, словоформы и артикулы, смысловая близость без общих слов.
- **Target encoding со сглаживанием** превращает id с сотнями тысяч значений в понятный модели признак «как часто здесь был контакт»; считается по обучающей части каждого разбиения — чтобы признак не содержал ни собственный таргет, ни таргеты валидационного фолда.
- **Cross-encoder** (эксперимент) читает пару запрос–заголовок целиком и учится на контактах, а не на «похожести текстов». 10 моделей — по одной на пару фолдов `{a, b}`, обученной на остальных трёх: в разбиении `k` строку фолда `f` оценивает модель `{f, k}`, строки фолда `k` и test — модель `{k, k+1}`, так что ни одна модель не видела ни оцениваемую строку, ни валидационный фолд.
- **5-фолдовый ансамбль**: оценка на одном фолде отличается от фолда к фолду (± 0.0007); среднее 5 моделей стабильнее одной.

## 7. Длинные выдачи

Окна с одинаковым текстом запроса внутри одного фолда склеены в псевдо-выдачи до 50 объявлений, относительные признаки пересчитаны по ним. NDCG@10 на псевдо-выдачах валидационных фолдов:

| Вариант | все псевдо-выдачи | только 25+ объявлений |
|---|---|---|
| random | 0.4107 | 0.1798 |
| сортировка по `click_conv` | 0.4197 | 0.1969 |
| модель, обученная на окнах (раздел 6) | 0.4913 | 0.2626 |
| модель, обученная на псевдо-выдачах | 0.4974 | **0.2850** |
| среднее двух моделей | **0.4978** | 0.2824 |

Разброс между фолдами для всех псевдо-выдач — 0.001–0.0016.

Вывод: обучение на псевдо-выдачах лучше обучения на окнах, и разница растёт с длиной выдачи: +0.006 на всех псевдо-выдачах и +0.022 (+9%) на выдачах из 25+ объявлений. Модель, обученная только на окнах, хуже отсекает дальний хвост выдачи, которого в окнах train нет. Среднее двух моделей и модель на псевдо-выдачах на всех псевдо-выдачах неразличимы (0.4978 против 0.4974 — меньше разброса); в основной `solution.csv` записано среднее — усреднение двух моделей обычно устойчивее, — а модель на псевдо-выдачах, лучшая на самых длинных выдачах, — в `solution_alt1.csv`.

## Что не сработало

- **Позиция строки в выдаче** — утечка из-за устройства train (окна вокруг контакта): NDCG ≈ 0.79 на валидации, бесполезна на test. Удалена.
- **Сырые id подкатегорий, регионов и объявлений как признаки** — миллионы значений, модель переобучается; заменены target encoding и признаками совпадения.
- **Полный текст описаний** — не помещается в память Colab; используется только длина.

## Воспроизведение

1. Положить `train-dset.parquet` и `test-dset-small.parquet` в корень Google Drive.
2. Открыть `Ad_Ranking_Colab.ipynb` в Colab, Runtime → Change runtime type → T4 GPU.
3. Runtime → Run all. Версии библиотек зафиксированы (первая ячейка, `requirements.txt`), все случайности, включая PyTorch, — `SEED = 42`. Эмбеддинги и оценки cross-encoder кешируются на Drive. Без GPU ноутбук отработает без эксперимента с cross-encoder — на итоговую модель это не влияет.
4. Результат — `solution.csv` (и `solution_alt*.csv`) в корне Drive.
